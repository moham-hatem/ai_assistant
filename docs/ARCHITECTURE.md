# بنية النسخة المحلية

## النطاق الحالي

- واجهة React متعددة اللغات لسؤال وجواب نصي، مع حفظ اختيار اللغة محليًا.
- API محلي يعمل كـVite middleware على نفس عنوان الواجهة.
- ملفات المعرفة محفوظة داخل `data/knowledge`.
- OpenCode Zen هو المسار الأساسي لإنشاء الإجابة، وNLLB هو مسار الترجمة المحلي عند تعطله.
- لا يُستخدم Supabase أو أي تخزين سحابي. يوجد سجل SQLite محلي دائم لمحاولات السؤال والإجابة، منفصل عن كاش الإجابات وذاكرة جلسة المتصفح.

## حدود الطبقات

```text
src/app                       تركيب الصفحة فقط
src/features/chat/api         عميل HTTP
src/features/chat/hooks       حالة المحادثة ومنطق الجلسة
src/features/chat/containers  ربط الحالة بمكونات العرض
src/features/chat/components  مكونات UI عرضية
src/features/admin            هيكل لوحة الإدارة وصفحاتها ومكوناتها
src/features/admin/question-logs  عميل سجل الأسئلة وحالته وقائمته وتفاصيله
src/features/admin/books      عميل الكتب وحالة القائمة/التفاصيل ومكونات إدارة الإصدارات

server/http                   التحقق من الطلب والاستجابة
server/answer-service         حالة الاستخدام الأساسية
server/knowledge              تحميل الملفات وترتيب الأدلة
server/documents              استخراج المستندات وحفظ الأصل والنص المرحلي محليًا
server/model                  OpenCode والـPrompt والتحقق
server/modules/question-log   عقد السجل وخدمته وتخزين SQLite وواجهات القراءة
server/modules/books          مجال الكتب والإصدارات وSQLite migrations وواجهات الإدارة
server/modules/reviews        طابور مراجعة المعلمين وقراراته وسجل أحداث SQLite غير القابل للتعديل
server/vite                   ربط الـAPI بخادم التطوير
server/create-runtime         إنشاء وربط الاعتماديات
```

تعتمد `AnswerService` على عقدي `KnowledgeSource` و`AnswerModel`، ولا تعرف Vite أو OpenCode أو نظام الملفات. لذلك يمكن إعادة استخدامها لاحقًا من Telegram أو خادم إنتاج دون نقل منطق الواجهة.

## تدفق الإجابة

```text
المتصفح
  -> POST /api/answer-question
  -> تحديد لغة الإجابة المختارة (ar / en / sw)
  -> توسيع تلقائي للمصطلحات إلى صيغ بحث متعددة اللغات مع كاش محلي
  -> بحث دلالي محلي متعدد اللغات في data/knowledge
  -> توسيع النتائج بالمقاطع السابقة والتالية من نفس الكتاب
  -> مقتطفات مرقمة
  -> DeepSeek عبر OpenCode Zen
  -> سباق نماذج احتياطية عند فشل الأساسي
  -> التحقق من رقم الدليل
  -> بوابة تحقق من لغة الإجابة المختارة
  -> مقتطف محلي مؤسس على الدليل إذا تعطلت جميع النماذج
  -> حفظ الإجابة الموثقة في الذاكرة المحلية
  -> تسجيل النتيجة والأدلة وزمن التنفيذ في SQLite بصورة لا تعطل الإجابة
  -> الإجابة أو اعتذار ثابت باللغة المختارة
```

## تدفق استيراد الكتب

```text
واجهة إدارة الكتب
  -> POST /api/knowledge/documents
  -> إنشاء BookEdition بحالة draft وبصمة SHA-256 للملف
  -> الانتقال إلى processing ثم استخراج النص
  -> حفظ الأصل والنص المرحلي في data/documents
  -> الانتقال إلى ready، من دون إتاحة الإصدار للبحث
  -> نشر الإصدار عبر دورة BookEdition
  -> البحث يحمل فقط نصوص الإصدارات المنشورة في SQLite
```

يدعم الاستيراد TXT وMarkdown وPDF ذي الطبقة النصية وDOCX. مستخرج PDF يرتب الأسطر مكانيًا ويستعيد التسلسلات الرقمية من الإنفوجرافيك قبل الفهرسة، ويمكن إعادة معالجة المصادر المحلية بأمر `npm run rebuild:documents`. لا ينفّذ OCR للصفحات المصورة بالكامل حتى الآن. تستخدم الملفات معرّفات UUID داخلية ولا تستخدم أسماء المستخدم كمسارات تخزين. لا يسمح الحذف بإزالة مستند مرتبط بتاريخ إصدار، حتى لا تصبح `originalDocumentReference` غير صالحة.

ينسق `BookDocumentService` بين مجال الكتب و`DocumentStore` من دون إدخال تفاصيل نظام الملفات إلى `BookService`. يحتفظ SQLite بالحالة المرجعية للمستندات المرتبطة؛ لذلك لا يقرأ `KnowledgeSource` نص مستند مرتبط إلا عندما تكون حالة إصداره `published`. يفحص النشر وجود النص أولًا، ثم تنفذ SQLite في معاملة واحدة نشر الإصدار وأرشفة الإصدار المنشور السابق.

للتوافق الانتقالي، يبقى `POST /api/knowledge/documents?name=...` صالحًا: ينشئ كتابًا ضمنيًا بلغة `und` وإصدارًا ثم ينشره قبل نجاح الطلب، وتظل الاستجابة القديمة التي تحتوي `document` صالحة. يمكن للمسار الصريح إضافة `bookId` و`version`؛ عندها ينتهي الرفع عند `ready` وتحتوي الاستجابة أيضًا `book` و`edition`، ويُجرى النشر عبر endpoint انتقال الإصدار. كذلك لا يسمح منسق runtime بنشر إصدار metadata يدوي لا يحمل مرجع `document:<uuid>` صالحًا ونصًا معالجًا؛ يجب رفع ملفه عبر المسار المرتبط أولًا.

يوجد grandfathered compatibility path مؤقت للمحتوى السابق: كل سجل صالح في `DocumentStore` metadata لا يرتبط بأي `BookEdition` يُعامل كمصدر منشور قديم، سواء بقي نصه في `data/knowledge/imported` أو انتقل بعد `rebuild` إلى `data/documents/text`. بمجرد ارتباط UUID بأي إصدار، يُحجب هذا المسار في كل الحالات ولا يظهر المستند إلا من خلال إصدار `published`، مما يمنع تسرب `draft` و`ready` و`rejected` و`archived` ويمنع ازدواج المنشور. ملفات `imported` الخام التي لا تملك metadata لا تُقرأ. سيُستبدل هذا المسار المؤقت لاحقًا بأداة migration صريحة تنشئ `Book` و`BookEdition` للمستندات القديمة، من دون مطالبة المستخدم بإعادة رفع الملفات الآن.

## حدود الثقة

وجود تعليمات للموديل لا يضمن وحده الالتزام بالمحتوى؛ لذلك توجد ثلاثة حواجز:

- لا تُستخدم إلا الملفات الموجودة في مجلد المعرفة المحلي.
- لا يُستدعى الموديل إذا لم يتطابق السؤال مع أي مقطع.
- لا تُمرر الإجابة للمستخدم إذا لم يذكر الموديل رقم دليل صالحًا.
- كل إجابة، بما فيها الإجابات القديمة من الكاش، يجب أن تجتاز فحص اللغة المختارة؛ النتيجة المخالفة تُحذف من الكاش ويُستدعى نموذج بديل.
- الإجراءات المرقمة لا تُمرر إذا نقصت خطواتها أو احتوت إضافات غير مدعومة، مع مراعاة لغة الإجابة المختارة.
- تعطل OpenCode لا يتحول إلى خطأ ظاهر للمستخدم ما دام هناك دليل؛ يُترجم الدليل المرتبط بالسؤال محليًا عبر NLLB دون إضافة معلومات من خارج الكتاب.
- الإجابات الموثقة تُخزن حسب السؤال واللغة والأدلة، وتُعاد من القرص قبل الاتصال بأي موديل.

ترسل الواجهة آخر ثماني رسائل كسياق لغوي للأسئلة المتتابعة. لا يُعامل هذا السياق كدليل، وتظل المعرفة المعتمدة محصورة في المقاطع المسترجعة من الملفات.

البحث الحالي يستخدم `multilingual-e5-small` محليًا لتمثيل السؤال والمقاطع، مع فهرس متجهي محفوظ بجوار المعرفة. يظل تطابق الكلمات خطة احتياطية إذا تعذر تشغيل النموذج المحلي. عند زيادة عدد الكتب بدرجة كبيرة يمكن نقل المتجهات إلى قاعدة متجهات دون تغيير عقد `KnowledgeSource`.

بعد ترتيب نتائج البحث، تحجز طبقة المعرفة جزءًا من حد الأدلة للمقاطع المتجاورة من الملف نفسه، ثم تعيدها بترتيبها داخل الكتاب. يسمح ذلك بتجميع تعريف أو قائمة بدأت في صفحة واستكملت في الصفحات التالية، من غير ربط `AnswerService` بتفاصيل الملفات أو الـPDF.

## الأمان

- `OPENCODE_API_KEY` يبقى في `.env.local` ولا يستخدم بادئة `VITE_`.
- الـAPI يعمل داخل خادم التطوير وليس داخل كود المتصفح.
- لا تُطبع المفاتيح في السجلات.
- حجم السؤال والجسم محدودان، ولكل محاولة OpenCode مهلة ستين ثانية، ومع فشل الأساسي تتسابق عدة نماذج مجانية احتياطية بدل انتظارها بالتتابع.
- النسخة المحلية ليست إعداد إنتاج عام؛ قبل النشر نحتاج مصادقة وحدود استخدام وتخزينًا مناسبًا.

## مرحلة لاحقة

ملفات Supabase الموجودة في المستودع مرجع غير نشط. قبل النشر العام نحتاج خادم إنتاج ومصادقة وصلاحيات وسياسات احتفاظ، ويمكن وقتها اختيار مخزن مناسب يطبق عقود المشروع من دون أن يصبح Supabase مطلوبًا للتطوير المحلي.
