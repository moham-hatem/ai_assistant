# اختبارات القبول المحلية

تشغّل مجموعة القبول مسار `AnswerService` مع بدائل ثابتة للبحث والنموذج. لا تستخدم شبكة، أو نموذجًا حقيقيًا، أو الملفات الموجودة في `data/knowledge`.

## التشغيل والـbaseline

```bash
npm run test:acceptance
```

يعرض Node نتيجة كل case بعلامة نجاح أو فشل، ثم ملخص أعداد `pass` و`fail`. وتظهر مدة كل اختبار بالميلي ثانية كتشخيص لزمن الـtest harness فقط؛ ليست SLO، ولا benchmark، ولا رقمًا من بيئة الإنتاج. الـbaseline المقبول هو نجاح جميع الحالات الست:

- إجابة عربية مستندة إلى دليل.
- امتناع إنجليزي عند غياب الدليل، حتى لو احتوى history على إجابة محتملة.
- سؤال «لماذا» وإجابة بالسواحيلية مع استبعاد النص المجاور غير المتعلق.
- سؤال إنجليزي مركب يسترجع دليلًا مستقلًا لكل جزء.
- إجراء عربي يحافظ على الخطوات المرقمة وترتيبها ويحذف النثر المجاور.
- سؤال عربي بإجابة إنجليزية لأن لغة الاستجابة المختارة هي الإنجليزية، مع دليل سواحيلي.

هذه المجموعة تكمل `test:local` ولا تحل محلها؛ فهي تمرر corpus مصطنعًا declarative عبر تعاون الخدمة والبحث والنموذج بدل تكرار اختبارات الوحدات لكل دالة.

## إضافة case

1. أضف fixture صغيرة إلى `tests/acceptance/fixtures.ts`: المدخل، ونتائج البحث لكل جزء من السؤال، ونتيجة النموذج الثابتة، والمخرجات المتوقعة.
2. استخدم معرفات تبدأ بـ`fixture:` واجعل النص قصيرًا بما يكفي لمراجعة سبب القبول أو الامتناع بالعين.
3. إذا كانت الحالة تثبت invariant جديدًا لا تغطيه المقارنات العامة، أضف assertion مركزة في `answer-service.acceptance.test.ts`.
4. شغّل `npm run typecheck` و`npm run test:acceptance`، ثم بقية فحوص المشروع قبل الدمج.

## سلامة الـfixtures

لا تنسخ كتبًا حقيقية، أو مقتطفات من كتب المستخدم، أو محادثات، أو سجلات تشغيل، أو أسماء وبيانات شخصية. لا تضف مفاتيح API أو tokens أو URLs خاصة أو أي سر. استخدم نصوصًا تعليمية مصطنعة وغير حساسة فقط، ولا تجعل fixture تقرأ من `data/knowledge` أو تتصل بالشبكة. إذا احتاجت الحالة مادة أطول، أنشئ ملخصًا خياليًا صغيرًا يثبت السلوك المطلوب دون محاكاة محتوى كتاب حقيقي.
