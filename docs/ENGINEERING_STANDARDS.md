# المعايير الهندسية

## 1. الهدف والنطاق

تطبق هذه المعايير على أي كود جديد أو تعديل جوهري في المشروع. غايتها الحفاظ على منتج محلي سهل الاختبار وقابل لاستبدال قنواته وتخزينه، مع فصل واضح بين العرض وحالات الاستخدام والبنية التحتية.

الأرقام الواردة حدود إرشادية وليست قواعد شكلية عمياء؛ تجاوزها مقبول عندما يزيد الوضوح، على أن يذكر سبب التجاوز في المراجعة ويُفصل الملف عندما يجمع أكثر من مسؤولية.

## 2. التنظيم Feature-first

تنظم قدرات المنتج حسب الميزة، لا حسب نوع الملف وحده. البنية الحالية في الواجهة مثال معتمد:

```text
src/features/<feature>/
  api/          عميل النقل وعقود استجابة الواجهة
  components/   عرض خالص قدر الإمكان
  containers/   تركيب حالة الميزة مع العرض
  hooks/        حالة وتنسيق تفاعلات الواجهة
  types.ts      أنواع الميزة العامة عند الحاجة
```

وعند نمو الخادم، تكون الوجهة المفضلة:

```text
server/features/<feature>/
  contracts/       العقود وDTOs الخاصة بالميزة
  use-cases/       حالات الاستخدام وقواعد التنسيق
  repositories/    واجهات التخزين وتطبيقاتها المحلية
  services/        خوارزميات أو سياسات مجال مركزة
  tests/           عند الحاجة لاختبارات عابرة للملفات
```

لا يلزم نقل الملفات الحالية لمجرد مطابقة شكل المجلدات. يُجرى النقل عندما تمس الميزة أو عندما تصبح الحدود الحالية عائقًا، مع إبقاء التغيير قابلًا للمراجعة.

تبقى الأجزاء المشتركة فعلًا فقط في `shared/` أو طبقة مجال صغيرة. لا يُستخدم `utils/` كمخزن عام لدوال غير مترابطة.

## 3. حدود الطبقات واتجاه الاعتماد

```text
UI component
  -> container/hook
  -> browser API client
  -> HTTP handler
  -> use case
  -> domain contracts
  <- repository/model adapter
```

### UI وlogic

- مكوّن العرض يستقبل props ويعرض الحالات ويرسل أحداثًا؛ لا ينفذ `fetch` ولا يقرأ نظام التخزين.
- الـhook أو container يدير حالة الشاشة والتنسيق، ولا يكرر قواعد المجال الموجودة في الخادم.
- عميل API مسؤول عن النقل والتحقق البنيوي الأولي وتحويل أخطاء الشبكة إلى أخطاء مفهومة للواجهة.
- قواعد مثل «لا إجابة بلا دليل» أو «الإصدار غير المنشور لا يُبحث» تبقى على الخادم داخل حالة استخدام/سياسة مجال، حتى لو أخفتها الواجهة أيضًا لتحسين التجربة.

### حالات الاستخدام

- لكل عملية ذات معنى اسم فعلي واضح، مثل `AnswerQuestion` أو `PublishBookEdition` أو `SubmitFeedback`.
- تستقبل حالة الاستخدام input محددًا وتعيد result محددًا، ولا تعتمد على `Request` أو `Response` أو React أو Vite.
- تنسق العقود والمعاملات والسياسات؛ لا تتولى parsing HTTP ولا تفاصيل مسارات الملفات.
- تمرر الاعتماديات صراحة في المنشئ أو factory، وتُتجنب singletons المخفية.

### Repositories وadapters

- يعرف عقد repository في طبقة الميزة/المجال، ويطبق في طبقة البنية التحتية المحلية.
- لا تُرجع واجهة repository مسار ملف داخليًا أو شكل JSON خاصًا بالتخزين إلى حالة الاستخدام.
- يتولى التطبيق المحلي الكتابة الذرية قدر الإمكان، والتحقق من الإصدار البنيوي، والتعامل الصريح مع التلف والترحيل.
- أي مخزن بديل مستقبلًا يطبق اختبارات العقد نفسها. لا تُضاف تبعية Supabase أو خدمة مدفوعة إلى المجال.

## 4. API handlers والعقود

### مسؤولية handler

يقتصر handler على:

1. مطابقة الطريقة والمسار.
2. قراءة الجسم ضمن حد الحجم.
3. parsing وvalidation إلى DTO موثوق.
4. استدعاء حالة استخدام واحدة أو منسق واضح.
5. تحويل النتيجة/الخطأ إلى استجابة HTTP متسقة.

لا يحتوي handler على بحث معرفي أو قرار اعتماد أو وصول مباشر متعدد الخطوات إلى التخزين.

### قواعد العقد

- لكل endpoint نوع طلب ونوع نجاح وأكواد أخطاء مستقرة.
- تحمل الاستجابات `requestId` للتتبع.
- لا يغيّر endpoint معنى حقل قائم بصمت؛ التغيير الكاسر يحتاج نسخة أو مسار ترحيل متوافقًا.
- تستخدم التواريخ ISO 8601 UTC، والمعرفات غير قابلة للتخمين حيث يلزم.
- لا ترسل الاستجابة stack trace أو مسارًا محليًا أو مفتاحًا أو تفاصيل مزود لا يحتاجها العميل.
- تُحدد الحدود رقميًا في مصدر مشترك عند استخدامها في العميل والخادم، مع تحقق خادمي نهائي.
- تُرجع الأدلة كمراجع منظمة (`bookId`, `editionId`, `chunkId`, موضع/صفحة وعنوان عرض)، لا كنصوص مبهمة فقط.

## 5. صغر الملفات والمسؤوليات

حدود إرشادية للكود، باستثناء الأسطر الفارغة والاستيرادات البسيطة:

| النوع | الهدف المعتاد | إشارة تستدعي الفصل |
| --- | ---: | ---: |
| React component أو hook | 40–120 سطرًا | أكثر من 150 |
| حالة استخدام/خدمة مجال | 60–150 سطرًا | أكثر من 200 |
| handler أو API client | 30–100 سطر | أكثر من 120 |
| repository adapter | 60–180 سطرًا | أكثر من 220 |
| ملف أنواع/عقود | 30–120 سطرًا | أكثر من 180 |
| ملف اختبار | 80–250 سطرًا | أكثر من 300 أو تعدد وحدات غير مترابطة |

كذلك:

- الدالة الواحدة تستهدف أقل من 40 سطرًا و3–4 مستويات تداخل كحد عملي.
- إذا احتاج الملف إلى وصف يحتوي «و»، فغالبًا يجمع مسؤوليتين.
- ملفات الخوارزميات المتماسكة، مثل تحليل تخطيط PDF، قد تتجاوز الحد إذا كان فصلها سيخفي التدفق؛ يلزم عندها اختبارات مركزة وأسماء أقسام واضحة.
- لا يُجرى تفتيت آلي ينتج ملفات وسيطة عديمة المعنى فقط لتحقيق رقم.

## 6. التسمية واللغة

- أسماء الملفات والمجلدات في الكود بالإنجليزية و`kebab-case`، ومكونات React بـ`PascalCase.tsx` كما في النمط الحالي.
- الأنواع والأصناف والمكونات `PascalCase`، والدوال والمتغيرات `camelCase`، والثوابت العامة `UPPER_SNAKE_CASE` عند ثباتها الحقيقي.
- تسمى حالات الاستخدام بفعل وموضوع، وتسمى repositories باسم الكيان: `AnswerRecordRepository`.
- تستخدم الأسماء مصطلحات المنتج المعتمدة: `book`, `edition`, `evidence`, `review`, `approvedAnswer`, `feedback`. لا تتبادل `document` و`book` إذا كان الفرق مقصودًا.
- Boolean يبدأ بـ`is/has/can/should` حيث يلائم، ولا تستخدم أسماء مختصرة إلا الشائعة جدًا مثل `id` و`url`.
- النص الظاهر للمستخدم يمر عبر i18n. رسائل التشغيل العربية الحالية مرحلة انتقالية؛ لا تضاف رسائل ثابتة جديدة في مكونات متعددة.
- التعليقات تشرح **لماذا** أو قيدًا غير بديهي، ولا تعيد صياغة السطر. لغة الكود والتعليقات التقنية الإنجليزية ما لم يكن النص تعليميًا عربيًا أو سببًا لغويًا يستلزم العربية.

## 7. الأخطاء والتسجيل والخصوصية

- تستخدم أخطاء مجال/تطبيق ذات `code` ثابت وحالة HTTP مناسبة عند الحافة.
- لا تستخدم الاستثناءات لمسار نجاح متوقع، ولا تبتلع الخطأ من دون fallback موثق أو تسجيل منقح.
- تسجل الأخطاء مع `requestId` وبيانات تشغيل غير حساسة؛ يمنع تسجيل المفاتيح، أجسام الكتب، السؤال الكامل، سجل المحادثة، أو إجابة المستخدم افتراضيًا.
- رسائل المستخدم قابلة للفهم ولا تكشف تفاصيل داخلية. يحفظ السبب التقني في سجل المشغل المنقح.
- كل fallback يملك شرط دخول واضحًا واختبارًا؛ لا تتحول أخطاء المزود إلى إجابة غير موثقة.

## 8. التخزين المحلي وقابلية الاستبدال

- التخزين الافتراضي ملفات محلية تحت `data/` ومجلدات مستبعدة من Git للمحتوى والكاش والنماذج.
- صيغة كل سجل دائم تحمل `schemaVersion`، وتكون الكتابة الذرية عبر ملف مؤقت ثم استبدال عند الإمكان.
- تفصل بيانات المصدر الأصلية عن النص المشتق والفهرس والكاش والسجل التشغيلي، ولكل منها سياسة حذف/إعادة بناء.
- لا يعتمد منطق المجال على `node:fs` أو أسماء مجلدات. هذه التفاصيل في adapter محلي.
- العقود تُصمم حسب احتياج حالة الاستخدام، لا حسب API لقاعدة بيانات محتملة.
- قبل اعتماد مخزن بديل يجب تشغيل suite اختبارات عقد مشتركة وإثبات الترحيل والرجوع. لا يبرر ذلك إضافة خدمة مدفوعة مبكرًا.

## 9. الاختبارات

### هرم الاختبار

- **وحدة:** سياسات المجال، parsing، ranking، التحقق من اللغة والجودة، وتحولات الحالات.
- **عقد:** كل repository/model/channel adapter باستخدام حالات نجاح وفشل موحدة.
- **تكامل:** handler + use case + adapter محلي داخل مجلد مؤقت، من دون شبكة حقيقية.
- **واجهة:** hooks/components للتفاعل والحالات الحرجة، ثم عدد صغير من رحلات end-to-end.
- **قبول معرفي:** corpus ثابت غير حساس يغطي اللغات الثلاث، غياب الدليل، الأسئلة المركبة، الإجراءات، والتعارض أو ضعف المصدر.

### قواعد الاختبار

- الاختبار حتمي؛ الشبكة والنماذج الخارجية والوقت العشوائي تستبدل ببدائل مضبوطة.
- اسم الاختبار يصف السلوك والنتيجة، لا اسم الدالة فقط.
- كل إصلاح عيب يضيف اختبار regression يفشل قبل الإصلاح.
- تختبر حالات الفشل والامتناع بقدر حالات النجاح، خصوصًا حدود المعرفة.
- لا توضع كتب حقيقية أو أسرار أو بيانات شخصية في fixtures.
- لا يكفي snapshot وحده لإثبات صحة إجابة معرفية أو قرار صلاحية.

الفحوص الإلزامية قبل الدمج:

```bash
npm run typecheck
npm run build
npm run test:local
```

يشغّل `npm audit` دوريًا وعند تغيير الاعتماديات، وتراجع نتائجه حسب قابلية الاستغلال في هذا المشروع بدل إصلاحات عمياء تكسر البناء.

## 10. TypeScript وجودة التنفيذ

- يبقى الوضع الصارم مفعّلًا، ويمنع `any` إلا عند حافة غير موثوقة مع narrowing فوري وسبب مكتوب.
- كل مدخل خارجي `unknown` حتى يمر بالتحقق.
- تستخدم union types للحالات المغلقة، وتكون تحولات الحالة صريحة.
- تفضل الدوال النقية للترتيب والتطبيع والتحقق، وتفصل I/O عنها.
- لا تمرر كائنات ضخمة عامة بين الطبقات؛ استخدم DTOs صغيرة ومقصودة.
- لا تُنشأ abstraction قبل وجود مسؤولية أو حد استبدال حقيقي، لكن التخزين والقنوات والنماذج الخارجية حدود استبدال مطلوبة من البداية.

## 11. Definition of Done للتغيير الهندسي

لا يعد التغيير مكتملًا إلا إذا:

1. يحقق معيار قبول مكتوبًا ولا يوسع نطاق المنتج ضمنيًا.
2. يحترم اتجاه الاعتماد ولا يضع منطق المجال في UI أو handler.
3. يغطي السلوك الجديد واختلالاته باختبارات مناسبة.
4. تمر فحوص النوع والبناء والاختبارات المحلية.
5. لا يضيف سرًا أو محتوى كتاب أو بيانات شخصية إلى Git أو السجلات.
6. يحدّث العقود والوثائق وملفات الإعداد النموذجية عند الحاجة.
7. يوضح أي migration أو إعادة فهرسة أو أثر على البيانات وخطة الرجوع.
8. يبقى قابلًا للتشغيل محليًا من دون Supabase أو خدمة مدفوعة.

## 12. قائمة مراجعة سريعة

- هل اسم الميزة ومكان الملف يعبّران عن مسؤولية واحدة؟
- هل يمكن اختبار حالة الاستخدام من دون React وVite ونظام ملفات حقيقي؟
- هل handler رقيق والعقد متحقق على الخادم؟
- هل كل إجابة أو قرار معرفي قابل للتتبع إلى دليل وإصدار؟
- هل التخزين خلف repository وهل كتابته وفشله آمنان؟
- هل غطيت الامتناع والأخطاء واللغات، لا المسار السعيد فقط؟
- هل السجلات منقحة من الأسرار والمحتوى الحساس؟
- هل تجاوز حجم الملف مبرر أم يكشف أكثر من مسؤولية؟
