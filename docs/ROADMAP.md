# خارطة طريق المنتج

## 1. طريقة قراءة الخارطة

الحالات:

- **تم:** معيار المرحلة متحقق في الكود الحالي.
- **جزئي:** توجد قدرة عاملة، لكن بقيت فجوات لازمة لاكتمال المرحلة.
- **ناقص:** لم يبدأ التنفيذ المنتج بعد.

ترتيب المراحل يعكس الاعتماديات، وليس وعدًا زمنيًا. لا تتطلب أي مرحلة Supabase أو خدمة مدفوعة؛ يبقى التخزين المحلي هو الأساس، وتُحفظ قابلية استبدال التخزين والهوية والجلسات من خلال العقود.

## 2. ملخص الحالة الحالية

| المجال | الحالة | الموجود | الفجوة الأساسية |
| --- | --- | --- | --- |
| واجهة المساعد | جزئي متقدم | دردشة ويب واختيار `ar/en/sw` واتجاه صحيح وfeedback لكل إجابة ناجحة | عرض الاستشهاد وإتاحة الوصول الأوسع |
| الإجابة المقيدة بالأدلة | جزئي | بحث دلالي، توسيع متعدد اللغات، تحقق دليل ولغة وإجراءات، امتناع آمن | تقييم قبول منظم وتتبع المصدر للمستخدم |
| إدارة الكتب | جزئي متقدم | رفع إصدار لكتاب محدد مع progress، معالجة مرتبطة بالإصدار، معاينة وإعادة معالجة OCR، بحث للمنشور فقط، نشر ذري واستعادة، وaudit دائم لاعتماد OCR، وواجهة إدارة فعلية محمية بالصلاحيات | ترحيل المحتوى القديم وأدوات التشغيل |
| التخزين | تم للنسخة المحلية | ملفات للكاش والكتب والفهرس وSQLite لسجل الأسئلة والمراجعات والإجابات المعتمدة وfeedback ومستخدمي الفريق وجلساتهم | سياسات الاحتفاظ والحذف والترحيل طويل المدى والنسخ الاحتياطي |
| سجل الأسئلة والأدلة | جزئي | سجل SQLite دائم وواجهة إدارة للقائمة والتفاصيل | ربط الكتاب والإصدار، الخصوصية والاحتفاظ، والفلاتر المتقدمة |
| مراجعات المعلمين | جزئي متقدم | Backend وواجهة طابور وتعيين وقرارات وسجل أحداث append-only، وaudit أمني دائم للقرارات، وإجابات معتمدة ذات نسخ وأولوية آمنة، وهوية المراجع من principal موثق | إعادة المراجعة الآلية عند تغير المصدر |
| لوحة المطورين | جزئي متقدم | إدارة الكتب والمراجعات والسجل ولوحة مقاييس فعلية ووصول الفريق، ومدخل محلي وحماية حسب الصلاحية | تشخيص أعمق وسياسات منصة إضافية |
| Telegram | جزئي محلي | long polling محلي، أوامر ولغات، جلسات HMAC، idempotency وrate limiting | أمان وتشغيل النشر الخارجي وسياسات الاحتفاظ |
| PWA | جزئي متقدم | manifest وأيقونات وservice worker محدود للغلاف، UX اتصال وتحديث مترجمة، handshake لإصدارات الواجهة وAPI، ومنع الإرسال offline أو عند عدم التوافق، والتحقق من إعادة فتح الغلاف دون خادم في production preview | اختبار تثبيت وتحديث فعليين والاتصال الضعيف والرجوع إلى online عبر HTTPS، ثم بوابة الأمان العامة |
| OCR | جزئي متقدم | استخراج هجين لكل صفحة، Poppler وTesseract محليان، حالات وثقة وإعادة معالجة ومراجعة إدارية، ومنع النشر قبل الجاهزية | تثبيت الأدوات في بيئة النشر وcorpus قبول حقيقي لكل لغة وتصحيح نص يدوي على مستوى الصفحة |
| أمان النشر العام | جزئي متقدم | دورة وصول محلية، وحارس صلاحيات رافض افتراضيًا، وسجل audit محلي tamper-evident بواجهة مراجعة، وتشخيص محدود، ونسخ احتياطية وصيانة restore/retention محلية fail-closed | rate limit دائم/موزع، وتشغيل production وHTTPS والأسرار، وتمرين تعافٍ دوري في بيئة شبيهة بالإنتاج |

**بوابة إلزامية قبل النشر العام:** مصادقة الفريق والتفويض الخادميان منفذان محليًا، لكنهما لا يكفيان وحدهما لجاهزية النشر. قد تبقى قنوات المتعلم في Telegram وPWA بلا تسجيل دخول حسب قرار المنتج؛ وقبل إتاحتها العامة يجب استكمال rate limits موزعة ومكافحة إساءة الاستخدام وسياسة البيانات والتشغيل الآمن ومتطلبات المرحلة 8. لا يمنع ذلك تطوير الـPWA محليًا.

## 3. المراحل

### المرحلة 0 — تثبيت خط الأساس المحلي

**الحالة: جزئي**

**الهدف:** جعل السلوك الحالي قابلًا للتشغيل والتقييم بصورة متكررة قبل إضافة قدرات إدارية.

**تم:**

- React وVite وAPI محلي على العملية نفسها.
- عقود `KnowledgeSource` و`AnswerModel` و`QuestionExpander` وحالة استخدام `AnswerService`.
- استيراد محلي للصيغ المدعومة، بحث دلالي متعدد اللغات، كاش محلي، ومسار ترجمة محلي احتياطي.
- فحوص `typecheck` و`build` واختبارات محلية لوحدات الإجابة والاسترجاع والمستندات والنماذج.
- مجموعة قبول مصطنعة بلا شبكة تغطي اللغات الحالية والامتناع والسؤال المركب والإجراءات واختلاف لغة السؤال والإجابة.

**المتبقي:**

- توسيع corpus القبول تدريجيًا بحالات محتوى يراجعها المسؤول التعليمي من دون نسخ كتب المستخدم.
- مقاييس baseline معرفية: دقة الاسترجاع، نسبة الإجابات المقبولة، معدل الامتناع، وزمن الاستجابة.
- توثيق سياسة استخدام المزود الخارجي والبيانات التي قد ترسل إليه.

**الاعتماديات:** لا شيء.

**معيار الانتهاء:** تنجح الفحوص على بيئة نظيفة، ويمكن تشغيل سيناريو قبول موثق للغات الثلاث، وتُسجل نتائج baseline ويوافق عليها المسؤول التقني ومسؤول المحتوى.

### المرحلة 1 — إكمال سلسلة الأدلة وتجريد التخزين

**الحالة: جزئي**

**الهدف:** جعل كل نتيجة قابلة للتتبع، وتجهيز المجال لإضافة السجلات من دون ربطه بنظام الملفات.

**تم:**

- تحمل الأدلة الداخلية `id` و`content`، وترجع استجابة API `requestId`.
- تعتمد حالة استخدام الإجابة على عقود بدل Vite أو نظام الملفات مباشرة.
- يوجد `QuestionLogRepository` وتطبيق SQLite محلي يسجل الإجابة أو الامتناع أو الفشل بصورة لا تعطل استجابة المستخدم.
- توجد واجهات قراءة داخلية محدودة للقائمة والتفاصيل، مع pagination وvalidation واختبارات استمرارية.

**المتبقي:**

- تطوير عقد سجل الإجابات مع نمو بيانات الإصدارات والمراجعات. عقود الكتب والمراجعات وfeedback وتنفيذاتها المحلية موجودة الآن.
- استكمال versioning وسياسات الترحيل والاحتفاظ لكل المخازن المحلية، بعد إضافة migrations مختبرة للكتب والمراجعات.
- إرجاع `EvidenceReference` آمن في عقد API وعرض المصدر والإصدار والمقطع في الواجهة.
- إضافة سياسة schema migrations وretention والحذف المنقح لسجل التدقيق الحالي.

**الاعتماديات:** المرحلة 0.

**معيار الانتهاء:** يمكن تبديل repository محلي ببديل اختباري في اختبارات حالات الاستخدام، وكل إجابة أو امتناع مسجلان مع الأدلة وإصدار المحتوى، ويظهر الاستشهاد للمستخدم.

### المرحلة 2 — حوكمة الكتب والإصدارات

**الحالة: جزئي متقدم — دورة الرفع والبحث والواجهة منفذة، وأدوات التشغيل الكاملة ناقصة**

**الهدف:** منع دخول محتوى غير مراجع إلى المساعد، والحفاظ على تاريخ الإصدارات.

**تم:**

- عقود `Book` و`BookEdition` وrepository قابل للاستبدال مع SQLite migrations.
- حالات `draft/processing/ready/published/rejected/archived` وانتقالات مختبرة.
- منع تكرار بصمة المحتوى داخل الكتاب، ونشر ذري مع rollback، واستعادة إصدار مؤرشف إلى `ready` قبل إعادة نشره.
- API داخلي لإنشاء الكتب والإصدارات وعرضها وتغيير الحالة، من دون نشر تلقائي.
- منسق application يربط الرفع بالاستخراج وحالات الإصدار، ويمنع غير المنشور من البحث مع مسار توافق آمن للمستندات القديمة ذات metadata.
- واجهة إدارة متعددة اللغات للقائمة والتفاصيل والإصدارات وpagination وانتقالات المشغل الآمنة، مع حماية من الاستجابات المتقادمة وإعادة مزامنة بعد النشر.
- رفع إصدار جديد من داخل تفاصيل الكتاب، مع رقم إصدار مطلوب وprogress وحماية من سباق تبديل الكتاب؛ ينتهي الإصدار عند `ready` ولا يُنشر تلقائيًا.

**المتبقي:**

- معاينة النص، إعادة المعالجة، وإظهار سبب فشل الاستخراج كإجراءات تشغيلية مسجلة.
- تحويل المستندات القديمة غير المرتبطة إلى `Book` و`BookEdition` بأداة migration صريحة ثم إزالة مسار التوافق المؤقت.
- إرجاع مراجع أدلة منظمة تحمل `bookId/editionId/chunkId` بدل الاعتماد على هوية نصية مشفرة فقط.

**الاعتماديات:** المرحلة 1، وقرار مالك المحتوى في نموذج البيانات وحالات النشر.

**معيار الانتهاء:** يمر كتاب اختباري بدورة مسودة → معالجة → نشر → إصدار أحدث → رجوع، وتبقى الإجابات القديمة مرتبطة بإصدارها ولا يظهر غير المنشور في البحث العام.

### المرحلة 3 — سجل المراجعة والإجابات المعتمدة

**الحالة: جزئي متقدم**

**الهدف:** تمكين المعلمين من الرقابة البشرية وإعطاء الإجابة المعتمدة أولوية قابلة للتدقيق.

**تم:**

- Backend محلي لطابور المراجعة والتصفية والتعيين وحالات القرار الأربع.
- تسجيل الإنشاء وتغيير الحالة والتعيين والتحرير والاعتماد والرفض كأحداث تدقيق ذرية append-only.
- ربط واجهة المراجعات بالـBackend المحلي مع التصفية والتصفح والإجراءات وسجل الأحداث.
- أخذ هوية المراجع من principal الجلسة الموثقة، مع فرض `content:review` خادميًا بدل معرّف يدخله المتصفح.
- إنشاء إجابات معتمدة ذات نسخ داخل نفس معاملة قرار الاعتماد، مع تقاعد النسخة السابقة وسجل غير قابل للتعديل الصامت.
- إعطاء التطابق المعياري exact في اللغة نفسها الأولوية قبل البحث والنموذج، بعد التحقق وقت الطلب من صلاحية كل الأدلة المنشورة.
- إدخال تغييرات الحالة وقرارات المعلمين في سجل audit أمني دائم ومحدود البيانات، من principal الموثق ومن دون نص السؤال أو الإجابة.

**المتبقي:**

- إدخال الإجابة تلقائيًا إلى إعادة المراجعة عند تغير المصدر بدل الاكتفاء بإيقاف أولويتها والعمل بالمسار العادي.

**الاعتماديات:** المرحلتان 1 و2.

**معيار الانتهاء:** يستطيع مراجع مخول معالجة حالة من بدايتها إلى اعتماد/رفض، وتُعاد الإجابة المعتمدة للسؤال المطابق، ويمكن التراجع من دون فقد السجل أو كسر الإحالات.

### المرحلة 4 — Feedback والقياس التشغيلي

**الحالة: تم للنسخة المحلية**

**الهدف:** تحويل إشارات المستخدمين إلى تحسينات قابلة للقياس لا إلى تعديلات تلقائية غير محكومة.

**تم:**

- مفيد/غير مفيد لكل إجابة ناجحة، مع أسباب مصنفة وتعليق اختياري محدود وidempotency من دون تخزين معرّف الإرسال الخام.
- إحالة ذرية إلى طابور المراجعة فورًا للمحتوى الحساس، أو عند ثالث تقييم غير مفيد للسؤال المعياري واللغة نفسيهما، مع منع مراجعة مكررة للحالة.
- لوحة `#/admin/quality` لمقاييس المحاولات والامتناع والأخطاء والرضا وتغطية feedback والتصعيد وزمن المراجعة واستخدام الإجابة المعتمدة.
- قاموس مقاييس ثابت وفلاتر UTC واللغة والقناة، وbreakdowns مجمعة من دون أسئلة أو إجابات أو تعليقات أو أدلة أو معرّفات فردية.
- لا يوجد فلتر كتاب/إصدار حتى تتوافر إحالة منظمة موثوقة؛ لا تُستنتج الهوية من نص الدليل.

**الاعتماديات:** سجل المرحلة 1 وطابور المرحلة 3.

**معيار الانتهاء:** يمكن تتبع feedback من النتيجة إلى قرار المراجعة، وتتطابق مقاييس لوحة عينة الاختبار مع الحساب اليدوي، ولا يعدل feedback المحتوى تلقائيًا.

### المرحلة 5 — PWA وتجربة الهاتف

**الحالة: جزئي متقدم — الأساس وUX الاتصال والتحديث وhandshake توافق API منفذة، واختبار غلاف offline نجح في production preview**

**الهدف:** تقديم تطبيق ويب قابل للتثبيت بتجربة اتصال واضحة وآمنة.

**تم:**

- manifest وأيقونات وmetadata، مع responsive وsafe-area و`prefers-reduced-motion` وإتاحة وصول للحالات.
- service worker محدود لغلاف التطبيق والأصول الآمنة، وسياسة مختبرة تبقي API والكتب والأسئلة والإجابات خارج cache المتصفح.
- حالة offline/online مترجمة للغات الثلاث في تطبيق المتعلم ولوحة الإدارة، مع تنظيف listeners ومنع إرسال سؤال offline دون حذف المسودة.
- إشعار تحديث ينتظر موافقة المستخدم الصريحة قبل طلب تطبيق service worker المنتظر وإعادة التحميل التابعة له.
- handshake بإصدارات صريحة بين الواجهة وAPI، مع إعادة الفحص عند عودة الاتصال، ومنع الإرسال عند عدم التوافق دون reload تلقائي.
- التحقق في `production preview` من manifest والأيقونات وتسجيل Service Worker، ثم إيقاف الخادم وإعادة فتح غلاف التطبيق بنجاح من cache الآمن.

**المتبقي:**

- اختبار التثبيت الفعلي من واجهة متصفح مدعوم ودورة تحديث حقيقية عبر HTTPS، بما يشمل الاتصال الضعيف والرجوع من offline إلى online.

**الاعتماديات:** استقرار عقد API في المرحلة 1؛ لا يعتمد على Telegram. يمكن تنفيذ الأعمال واختبارها محليًا قبل اكتمال المرحلة 8. لا تشترط الإتاحة العامة تسجيل دخول المتعلم؛ عزل الإدارة وحماية admin APIs منفذان محليًا، وتبقى الإتاحة العامة معتمدة على بقية متطلبات المرحلة 8 وrate limits الموزعة ومكافحة إساءة الاستخدام وسياسة بيانات للواجهات العامة.

**معيار الانتهاء:** ينجح اختبار التثبيت والتحديث والعمل في ظروف اتصال ضعيفة، ولا يدعي التطبيق إجابة offline غير متاحة، وتنجح مراجعة cache والخصوصية.

### المرحلة 6 — قناة Telegram

**الحالة: جزئي محلي — القناة العاملة محليًا منفذة، وجاهزية النشر الخارجي ناقصة**

**الهدف:** إعادة استخدام حالات الاستخدام نفسها من قناة مراسلة من دون ازدواج منطق المنتج.

**تم محليًا:**

- adapter للرسائل الخاصة و`/start` و`/language` واختيار `ar/en/sw`، مع تقسيم الردود الطويلة بأمان.
- long polling تسلسلي قابل للإيقاف، وclaim ذري مع lease/retry لمنع المعالجة المتزامنة والتعافي بعد الفشل.
- SQLite مستقل يحفظ مفتاح جلسة HMAC واللغة فقط؛ لا يحفظ chat id الخام أو السؤال أو history.
- rate limiting لكل جلسة، وhistory قصيرة في الذاكرة، وإدراج `telegram` في سجل الطلب.

**المتبقي:**

- نموذج تهديد وتشغيل ومراقبة ونسخ احتياطي وسياسة احتفاظ/حذف قبل أي نشر خارجي.
- قرار الاستضافة والسعة والتحقق التشغيلي؛ webhook خارج نطاق النسخة المحلية الحالية.

**الاعتماديات:** المرحلتان 1 و4. يمكن تطويرها محليًا بالتوازي مع المرحلة 5 بعد ثبات العقود. لا تشترط الإتاحة العامة تسجيل دخول المتعلم؛ مصادقة الفريق وتفويض الإدارة وعزل admin APIs منفذة محليًا، وتبقى الإتاحة العامة معتمدة على بقية متطلبات المرحلة 8 وrate limits الموزعة ومكافحة إساءة الاستخدام وسياسة بيانات للقناة العامة.

**معيار الانتهاء:** تعطي القناتان نتيجة معرفية متكافئة لنفس المدخل، ولا تعيد معالجة update مكرر، وتنجح اختبارات الأسرار والحدود والخصوصية.

### المرحلة 7 — OCR ومراجعة جودة الاستخراج

**الحالة: جزئي متقدم**

**الهدف:** استيعاب الكتب المصورة مع منع نشر نص منخفض الثقة.

**الأعمال:**

- **تم:** اكتشاف الصفحات المصورة أو ضعيفة النص وإدخال الصفحات المطلوبة فقط إلى OCR محلي عبر Poppler وTesseract.
- **تم:** حفظ ترتيب الصفحات وطريقة المعالجة وعدد صفحات OCR ومتوسط الثقة وحالات `ocr_required` و`review_required` و`failed`.
- **تم:** حفظ الأصل عند غياب الأدوات، ومنع النشر قبل الجاهزية، وإعادة المعالجة والمعاينة والموافقة الإدارية من دون نشر تلقائي.
- **متبقٍ:** تحرير نص الصفحة يدويًا مع سجل تدقيق، ومجموعة تقييم عربية/إنجليزية/سواحيلية وحد قبول يقره مدير المحتوى.
- **متبقٍ:** تثبيت Poppler وTesseract وحزم اللغات في بيئة النشر واختبارها على كتب حقيقية متنوعة.

**الاعتماديات:** حوكمة الإصدارات في المرحلة 2 ولوحة المراجعة في المرحلة 3. اختيار المحرك قرار تقني مستقل، ولا يفترض خدمة مدفوعة.

**معيار الانتهاء:** يعالج corpus القبول ضمن حد الجودة المتفق عليه، ولا يدخل نص منخفض الثقة في الفهرس المنشور قبل المراجعة، ويمكن إعادة المعالجة من الأصل.

### المرحلة 8 — أمان الإدارة وجاهزية النشر والاستبدال التشغيلي

**الحالة: جزئي متقدم — حماية الإدارة المحلية منفذة، وجاهزية النشر العام غير مكتملة**

**الهدف:** الانتقال من وضع محلي موثوق إلى تجربة مضبوطة أو استضافة عامة، فقط عند اتخاذ قرار بذلك، من دون الخلط بين إخفاء واجهة الإدارة وحمايتها.

**تم:**

- حسابات وجلسات فريق محلية في SQLite، وكلمات مرور `scrypt` مملّحة، ورموز جلسات عشوائية لا يخزن منها الخادم إلا hash.
- صفحة دخول مستقلة `#/admin/login`، وإخفاء رابط الإدارة عن الـanonymous، وعدم حفظ كلمة المرور أو token أو principal في تخزين المتصفح.
- cookies من نوع `HttpOnly; SameSite=Strict; Path=/`، مع `Secure` واسم `__Host-` في production، وانتهاء خامل ومطلق، وتدوير عند الدخول، وإلغاء عند الخروج أو تحديث كلمة المرور/الأدوار.
- تحقق same-origin للدخول والخروج والكتابات الإدارية بالاعتماد على `AUTH_PUBLIC_ORIGIN` الموثوق؛ ويتطلب production أصل HTTPS.
- حارس صلاحيات رافض افتراضيًا لكل `/api/internal/**` وواجهات إدارة المستندات، مع فصل الأدوار والصلاحيات وعدم وراثة `admin` لصلاحيات المحتوى.
- اشتقاق هوية المراجع واعتماد OCR عند حدود الخادم من principal الموثق، وأمر `npm run auth:user` لإنشاء مستخدمي الفريق المحليين أو تحديثهم.
- rate limit محلي في الذاكرة لمحاولات الدخول الفاشلة، مع رسالة موحدة للحساب الغائب وكلمة المرور الخاطئة.
- سجل audit أمني محلي مستقل في SQLite للأحداث الحساسة، append-only في الاستخدام العادي ومترابط بـHMAC مع key versions وintegrity API، وoutbox ذري داخل قواعد auth/books/reviews لإعادة التسليم؛ السجل tamper-evident وليس tamper-proof.
- صفحات إدارية مستقلة لمراجعة سجل الأمان وسلامة سلسلته، وتشخيص قواعد البيانات والتخزين وإعداد النموذج وأدوات OCR من دون كشف الأسرار أو المسارات الخارجية.
- نسخ احتياطية محلية محددة الإصدار بصيغة `.ilabackup`، تستخدم snapshot متسقًا لقواعد SQLite وmanifest وبصمات SHA-256، مع واجهات محمية للإنشاء والقائمة والفحص والتنزيل.
- أوامر صيانة preview-first للاستعادة والاحتفاظ، بتأكيدات مرتبطة بالبصمات، وفحوص schema/HMAC على نسخ مؤقتة، وjournal وrollback وadmission lock مشترك بين Vite وTelegram وأوامر الكتابة؛ لا توجد استعادة أو إزالة عبر HTTP.
- تقسيم تحميل لوحة الإدارة وصفحاتها إلى حزم مستقلة لا تُحمّل قبل المصادقة والصلاحية، مع Error Boundary مترجم لفشل تحميل الحزم.

**المتبقي قبل أي نشر عام:**

- نقل دورة الوصول المحلية المنفذة (الدعوات والاستعادة والحسابات والجلسات) إلى تشغيل إنتاجي مراقب ومختبر عبر HTTPS.
- rate limit دائم أو موزع يعمل بصورة صحيحة عند تشغيل أكثر من نسخة، وحماية إساءة استخدام مستقلة للواجهات العامة.
- تقوية تشغيل سجل audit قبل النشر العام: إدارة مفاتيح واحتفاظ ومراقبة وتنبيه خارجي مختبر، مع اختبار النسخ والاستعادة في بيئة شبيهة بالإنتاج.
- خادم production فعلي وHTTPS وإدارة أسرار وتدويرها، واختبار الاستعادة والrollback وفقد العملية دوريًا في بيئة شبيهة بالإنتاج، وسياسات احتفاظ وحذف وخصوصية ونسخة خارج الجهاز.
- مراجعة أمنية ونموذج تهديدات، ومراقبة منقحة، واختبارات حمل وسعة، وخطة ترحيل ورجوع وتوافق نسخ.
- اختبار عقود repositories والهوية والجلسات ضد بديل ذاتي الاستضافة أو مزود يُعتمد لاحقًا إذا احتاجت السعة؛ لا يغير حالات الاستخدام ولا يفترض Supabase أو خدمة مدفوعة.

**الاعتماديات:** المراحل 1–4 على الأقل، والقناة المراد نشرها من المرحلتين 5 أو 6.

**معيار الانتهاء:** تفشل طلبات الإدارة غير المصرح بها من جهة الخادم، وتنجح اختبارات الجلسات وCSRF والإلغاء والحدود والدعوات والتدقيق والأسرار وتعذر bypass في production، ثم تجتاز مراجعة الأمان والخصوصية والاستعادة وأهداف السعة وتجربة الترحيل والرجوع، ويوافق مدير المشروع على نموذج التشغيل والتكلفة.

## 4. بوابات القرار

لا يبدأ العمل التالي قبل موافقة مدير المشروع/المالك المختص:

1. **نموذج الحوكمة:** من يملك صلاحية نشر كتاب واعتماد إجابة، وهل يلزم مراجع واحد أم اثنان؟
2. **سياسة الأدلة:** مقدار النص الذي يمكن عرضه للمستخدم، خصوصًا للكتب ذات الحقوق.
3. **سياسة البيانات:** مدد الاحتفاظ بالأسئلة والسجلات وfeedback، وإمكان الحذف أو إخفاء الهوية.
4. **سياسة المزود الخارجي:** هل يسمح بإرسال أسئلة المستخدمين ومقاطع الكتب إلى OpenCode في كل بيئة أم في بيئات محددة فقط؟
5. **أولوية القنوات:** PWA أم Telegram أولًا بعد اكتمال سلسلة الأدلة.
6. **معيار OCR:** المحرك المحلي ومجموعة القياس والحد الأدنى المقبول لكل لغة.
7. **هدف النشر:** جهاز فردي، شبكة مؤسسة، أم خدمة عامة؛ لأنه يحدد المصادقة والسعة والتشغيل.
8. **مزود الهوية والجلسات:** حل ذاتي الاستضافة أم مزود خارجي بعد تقييم التهديدات والتكلفة والاستعادة؛ لا اختيار افتراضي لـSupabase أو خدمة مدفوعة، والعقود تبقى قابلة للاستبدال.

## 5. تعريف الانتهاء العام لكل مرحلة

بالإضافة إلى معيارها الخاص، لا تعد أي مرحلة منتهية إلا إذا:

- كتبت العقود وحالات الفشل ومعايير القبول قبل دمج التنفيذ.
- أضيفت اختبارات وحدة وتكامل مناسبة، ونجحت `npm run typecheck` و`npm run build` و`npm run test:local`.
- لا تحتوي السجلات أو fixtures أو Git على أسرار أو كتب فعلية أو بيانات مستخدمين حساسة.
- حدّثت وثائق المنتج والبنية والتشغيل إذا تغير السلوك أو العقد.
- أمكن تشغيل القدرة محليًا دون خدمة مدفوعة، أو وُثق البديل المحلي بوضوح إذا قررت الإدارة تكاملًا اختياريًا.
